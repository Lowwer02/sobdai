# Sobdai M1.3A payment verification operator contract

Migration `103_payment_verification_m1_3_expand.sql` is intentionally shadow-only. Run the complete file as one migration batch through the normal migration runner, or paste the complete file into a SQL editor inside an operator-controlled transaction. The file pins its initial transaction search path to `public` and qualifies extension functions; do not execute selected sections or deploy the application before the database objects, grants, and defaults have been checked.

Immediately after the migration, verify that `payment_settings.auto_approval_enabled = false` and `payment_settings.legacy_replay_backfill_complete = false`. The application may write bounded analyzer results in shadow mode, but no order, submission, entitlement, or notification can be changed by the shadow runner.

## Legacy approved-evidence replay

Run the service-only tool sequentially with the v1 HMAC configuration and the explicit guard:

```sh
PAYMENT_VERIFICATION_LEGACY_BACKFILL_CONFIRM=YES_I_AM_RUNNING_SOBDAI_PAYMENT_M13A_LEGACY_BACKFILL \
PAYMENT_VERIFICATION_HMAC_ACTIVE_VERSION=v1 \
PAYMENT_VERIFICATION_HMAC_SECRET_V1="$(openssl rand -hex 32)" \
npm run payment:m13a:legacy-backfill
```

The v1 secret must be exactly 64 hexadecimal characters (32 random bytes). The application decodes this hex representation with `Buffer.from(secret, 'hex')` before passing the 32 bytes to the canonical HMAC helper. The old pre-production implementation that passed the 64-character UTF-8 hex string to HMAC is not compatible and MUST NOT be used. Do not use an example, repeated-byte, or placeholder value; the application never generates or logs a Production secret. The tool reads only pre-cutoff approved submissions, fetches bounded keyset pages ordered by `(reviewed_at, id)`, downloads private objects through the service client, runs the same analyzer identity extraction, and records a durable result for every item. The database checkpoint advances with each recorded row, so an interrupted run resumes without a first-page loop. Missing objects, PDFs, unreadable evidence, unsupported references, and analyzer errors remain explicit unsupported outcomes. It never changes `orders.status`, package access, submission status, or notifications. A nonzero unsupported count leaves the activation fence false and exits with `BLOCKED`; rerunning is idempotent.

Automatic approval is not eligible for activation unless the completion RPC reports zero missing/unsupported results and `legacy_replay_backfill_complete = true`. There is no customer-facing flag for this operation.

The activation-settings RPC is `service_role`-only. Do not expose it through an admin page or client action; the ordinary application settings surface cannot enable the flag.

For a disposable local PostgreSQL verification run, apply the released M1.2/notification migrations and 103 to a loopback database named `sobdai_m13a_payment_test_<suffix>`, then run the committed suite with `M1_3A_PAYMENT_DB_ALLOW_DESTRUCTIVE_TESTS=YES_I_AM_USING_SOBDAI_PAYMENT_M13A_DB_TEST`, `M1_3A_PAYMENT_DB_LOCAL_ONLY=YES_I_AM_USING_SOBDAI_LOCAL_DB_ONLY`, and `M1_3A_PAYMENT_DB_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:<port>/sobdai_m13a_payment_test_<suffix> npm run test:payment-m13a-db`. The harness uses independent PostgreSQL connections and asserts final order, submission, verification, approved-evidence ledger, provider-attestation, event, and notification states, including row counts, linkage, orphan absence, and duplicate-`VERIFIED` provider-transaction absence for each financial race.

## HMAC v1 and rotation

Reference fingerprints use only `hmac-sha256:v1:<hex>` with `PAYMENT_VERIFICATION_HMAC_SECRET_V1` and `PAYMENT_VERIFICATION_HMAC_ACTIVE_VERSION=v1`. A missing, malformed, repeated, weak, or mismatched configuration makes the analyzer manual-only; it never falls back to plain SHA-256 for reference identity. M1.3A deliberately pins the active implementation to v1, so setting a future version before its re-key plan exists fails closed rather than silently creating a second identity namespace. Do not rotate the v1 secret while approved v1 ledger rows exist without a dedicated, tested migration/dual-key procedure.

## Hybrid triage and provider attestation

Offline results use `STRONG_MATCH`, `MANUAL_REVIEW`, `SUSPICIOUS`, or `ANALYZER_ERROR`. `STRONG_MATCH` means only that the submitted evidence is internally consistent and suitable for faster human review. It never means bank/provider confirmation, transaction existence, entitlement eligibility, or safe automatic approval. Payment-request QR and slip-verification QR are tracked separately; a valid CRC and extracted reference remain non-authoritative.

The future `auto_approve_payment_verification(uuid)` primitive is service-only and requires a matching durable `payment_provider_attestations.status = 'VERIFIED'` row from the allowlisted provider method, linked to the same order, submission, verification, reference fingerprint, amount, and supplied identity fields. A `VERIFIED` row must carry the canonical `(provider, method, provider_transaction_identity)` namespace, `provider_transaction_at`, `provider_verified_at`, and `valid_until`; `provider_verified_at` cannot precede the transaction, and `valid_until` must be later than verification. The current `promptpay_provider_api_v1` contract treats `valid_until` as the provider's explicit freshness boundary, not a universal business-age timeout. AUTO requires `provider_transaction_at >= order.created_at - interval '5 minutes'`, rejects expired rows, and rejects future transaction/verification times beyond five minutes of database clock skew. The transaction-age comparison is intentionally against order creation, not submission/upload creation: delayed uploads may arrive hours or the next day after a valid transfer. The five-minute value is clock tolerance only, not a historical-transaction allowance. A method without a known validity contract fails closed. The partial unique index on `(provider, method, provider_transaction_identity)` applies to `VERIFIED` rows only: failed/unavailable attempts may repeat, while a duplicate `VERIFIED` retry must resolve to the existing authoritative row and cannot create a second consumable attestation. M1.3A contains no provider adapter or application path that can create `VERIFIED`; the table has no client/service-role insert grant. Keep `auto_approval_enabled = false`.

To rotate the key in a future reviewed change: keep automatic approval disabled; stop analyzer workers; re-analyze every approved evidence object (pre-cutoff legacy rows and all live ledger rows) with the new version; write the new versioned identities while retaining/checking the old identities for the transition; verify reference/raw/normalized uniqueness and replay races; only then switch the active version. Never replace the secret in place or enable a new version without that complete re-key/dual-check step. If the re-key tooling and ledger plan are not present, keep v1 active and auto approval off. Re-run the disposable PostgreSQL concurrency suite and a real-slip corpus review before considering any future activation. M1.3A does not authorize activation as part of this rollout.

OCR remains fail-closed with a single bounded worker: concurrent calls return `OCR_BUSY`, timeout terminates and recreates the worker, and OCR failures become manual review/analyzer error. A serverless worker pool is a separate reviewed change, not an automatic-approval prerequisite for this shadow release.

The Next output-tracing include is route-scoped to `/api/payment/manual/slip` and the explicit `/admin/orders/[id]` resume surface; there is no global OCR include and the public root trace contains no OCR assets. The current `/admin/orders` list trace still inherits the worker/WASM/language files through the shared server-action module that also exports the detail-page resume action. Splitting that module would be a broader architectural change, so this bounded trace overhead is accepted as the remaining LOW operational finding for M1.3A; no runtime model download is used.
