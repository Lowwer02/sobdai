## Architecture decisions taken (spec ambiguities — user did not answer; proceeding with the spec-consistent default in each case)

**D1 — Confidence reduction rule** (resolves spec self-contradiction §5.3 vs §5.6/AP-12).
Decision: **Confidence = 'reduced' iff any IG-2 axis (blueprintType/learningObjective/questionPattern/section) is null/incomplete.** Reason string names the first missing axis (e.g. `"blueprintType axis missing (IG-2 gap)"`). Deterministic; driven by the Completeness facet; requires ZERO inference (the §5.3 "inferred from tags" example is treated as stale prose — honoring §5.6 + AP-12 which are normative MUST NEVER rules).

**D2 — Validation scope** (resolves §7.2 vs §7.3 + E-2B's targetCount=0 reality).
Decision: **Validate what is checkable; emit existence Warnings for gaps; honor the per-axis boundary.**
- **Empty pool** → Blocking (§11.2).
- **CR-1 with concrete `document_topic_pairs` binding, unmet by the pool** → Blocking (covers "impossible requirement" at the per-axis level the Generator is allowed to detect; joint infeasibility stays Solver's job per §7.3).
- **LO completeness vs `loDistribution.targets`** → Pass/Warning/Blocking (the only axis with real targets).
- **Document Registry entry with zero candidates** → Warning (covers "missing required documents").
- **L1 duplicate diversity** (distinct Topic×Difficulty×Pattern per Set; "Type"≡"Pattern" per §5.5/§3.2 axis vocabulary) → Warning if distinct-combinations < perSet.
- **Difficulty/Pattern count-completeness** → Pass (target=0; Solver derives counts; §7.3 boundary).
- **Exclusion post-condition** → asserted, not a real check (§7.2 says "shouldn't happen" since E-2C's Exclusion Filter ran first).

**D3 — Tier derivation failure** (resolves §11.2 "Fatal per-Question or Blocking per-Pool"). Cannot occur post-filter: **E-2C's Document Filter guarantees every row reaching Discovery has `document ∈ plan.permittedDocuments`** (which is `documentRegistry[].name`). So every row's Tier derivation succeeds. No Tier-failure path is needed; documented as a guaranteed-upstream invariant, not implemented.

**D4 — "Conflicting Metadata" / "Duplicate metadata inconsistency"** (resolves §11.2 under-definition). E-2C's filters already reject out-of-enum Difficulty/Pattern/LO and non-Published status before Discovery sees the row. The one remaining conflict class is **two Bank rows with the same Question Code but differing metadata** (a Bank integrity violation). Discovery detects this and emits a Blocking entry (per-Code conflict). Code is identity (§5.4); a duplicate Code is a data-quality conflict.

## Design — Discovery (`discoverCandidates`)

### Public API
```ts
export interface DiscoveryInput {
  readonly rows: readonly SyntheticBankRow[]   // E-2C FilterStageResult.rows
  readonly plan: QueryPlan
}
export type DiscoveryResult =
  | { readonly ok: true; readonly pool: CandidatePool }
  | { readonly ok: false; readonly fatalDiagnostics: readonly FatalDiagnostic[] }

export function discoverCandidates(input: DiscoveryInput): DiscoveryResult
```
Pure, deterministic, no I/O, no clock. `ok:false` only on Fatal (malformed Bank metadata per §2.2 "Fatal on malformed Bank metadata" — e.g. a duplicate Code conflict that prevents constructing a coherent pool).

### Materialization per row (5 facets per §5.2)
For each `SyntheticBankRow`, build a `Candidate`:

| Facet | Source / rule |
|---|---|
| **Identity** | `{ questionCode: row.questionCode, questionId: row.questionCode }` (the Bank has no separate UUID; Code IS identity per §5.4. `questionId` carries Code for now — documented as v1.0 simplification). |
| **Metadata** | Direct copy of `document`, `difficulty`, `topic`, `status` (narrowed to `QuestionStatus`); IG-2 axes copied with `null`-normalization (`undefined → null`). **Tier DERIVED** via Document Registry name→tier lookup (always succeeds per D3). `tags: []`, `category: null` (not on `SyntheticBankRow` v1.0). |
| **Completeness** | Per IG-2 axis: `'complete'` if value is non-null, else `'incomplete'`. |
| **Confidence** | Per D1: `'reduced'` if any IG-2 axis incomplete, else `'full'`. `reason` = first missing axis name when reduced, else `null`. |
| **Provenance** | `filtersPassed: [...FILTER_EXECUTION_ORDER]` (every surviving row passed all 7 — E-2C guarantees this). `eligibleSlots`: computed from the row's axes against `plan.{difficulty,pattern,learningObjective}Slots` (the slots whose `axisValue` matches the row's value, for every Set). `coverageSatisfied`: CR-1 rule ids whose `document_topic_pairs` binding the row matches (using E-2C's exported `Cr1DocumentTopicBinding`). `source: { kind: 'metadata_query', queryId: '<derived-stable-id>' }`. |

### Duplicate-Code conflict (D4)
If two rows share `questionCode` but differ in any metadata field → Fatal `internal_error` (or a Blocking ShortfallEntry — see below; choosing Blocking per D4 to allow the rest of the pool to proceed to Human Review). The conflict is recorded once; the offending Code is identified.

Actually — re-reading D4: a duplicate Code is a Bank-integrity issue. The cleanest fit is a **Blocking ShortfallEntry on axis `'duplicate_diversity'`** isn't right (that's L1). There's no perfect `ShortfallAxis` for "Bank duplicate Code." To stay within FROZEN contracts (no new axis), I'll surface this as a **Fatal `internal_error`** with the offending Code named — halting the run, which is the safe posture for a Bank integrity violation. The Conflict is then visible in `fatalDiagnostics`, not the ShortfallReport. (This matches §2.2 Discovery's "Fatal on malformed Bank metadata.") Decision recorded; the test "duplicate metadata inconsistency" exercises this Fatal path.

## Design — Pool Validation (`validatePool`)

### Public API
```ts
export interface PoolValidationResult {
  readonly pool: CandidatePool                          // unchanged (Validation never mutates)
  readonly shortfallReport: ShortfallReport             // FROZEN contract — no new diagnostic model
  readonly classification: GeneratorSeverity            // worst severity across entries (Pass if empty)
}
export function validatePool(pool: CandidatePool): PoolValidationResult
```
Pure. **Reports only — never repairs, expands, or weakens** (§7.5). The worst entry severity becomes `classification`; an empty `entries[]` → `classification: 'Pass'`.

`PoolValidationResult` is a NEW name — but it composes ONLY FROZEN contract types (`CandidatePool`, `ShortfallReport`, `GeneratorSeverity`). The task says "never invent a new diagnostic model" — `PoolValidationResult` is not a diagnostic model, it's a thin carrier for the FROZEN `ShortfallReport` plus a worst-severity rollup. No new severity, no new axis, no new entry shape. This is the minimal carrier the §2.2 "Validated Pool + Shortfall Report" output contract requires.

### Checks (per D2)
1. **Empty pool** → Blocking entry, axis `'coverage'`, setNumber null. (§11.2 Empty Pool.)
2. **CR-1 coverage** (only when binding is `Cr1DocumentTopicBinding`): for each bound `(document, topic)` pair, if no Candidate matches → Blocking entry, axis `'coverage'`, setNumber null, explanation names the missing pair. (§7.2 Coverage Completeness; §11.2 Partial Coverage.)
3. **LO completeness**: for each Set × LO slot in `plan.learningObjectiveSlots`, count Candidates with that LO; classify Pass (≥ target), Warning (== target, no headroom), Blocking (< target). (§7.2 LO Completeness — the one axis with real targets.)
4. **Document existence**: for each `plan.permittedDocuments` entry with zero Candidates → Warning entry, axis `'document'`, setNumber null. (Covers "missing required documents.")
5. **L1 duplicate diversity**: for each Set, count distinct `(topic, difficulty, pattern)` tuples among Candidates; if < `perSet` → Warning, axis `'duplicate_diversity'`, setNumber = that Set. (§7.2 Duplicate Constraints, L1 only.)
6. **Difficulty/Pattern** → no entry (target=0; Solver's job).
7. **Exclusion post-condition** → asserted in a test, not emitted (§7.2 "shouldn't happen").

### Severity rollup
`classification = worst(entries.severity)` with ordering Pass < Warning < Blocking < Fatal. No Fatal entries emitted by Validation (Fatal is reserved for IG-2 missing-axis, which E-2C already caught upstream, and for Discovery's malformed-Bank path).
