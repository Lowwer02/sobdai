## Design — short version

### Operating layer: Bank rows, NOT Candidates
Per Architecture §4.1 ("Apply the Query Plan's filters to **Bank metadata**, producing the set of eligible rows") and §4.4 ("Does NOT materialize Candidates"), the filters operate on **Bank rows** (`SyntheticBankRow[]`). The output is filtered rows + a rejection log — NOT `Candidate` objects. Candidate materialization belongs to Discovery (F-2.3). This keeps E-2C strictly Stage 2.

### Bank access via injected adapter (README §2 compliance)
"DB/Bank reads happen in the Generator's filter layer only (and the Generator's filter adapters are injected, not imported)." E-2C introduces a minimal `BankReadAdapter` interface:

```ts
export interface BankReadAdapter {
  /** Initial metadata read before filtering (Stage 2 input). Pure on the contract;
   *  concrete production adapter hits the Bank read-only. */
  readMetadata(): ReadonlyArray<SyntheticBankRow>
}
```
- Tests use an in-memory adapter wrapping `buildBankRow(s)`.
- `metadata-filters.ts` imports ZERO Supabase (verified by a test asserting no `supabase`/`createClient`/`select(` strings, mirroring the E-2B planner test pattern).
- E-2C defines this interface locally in `metadata-filters.ts` (not in contracts.ts — that's forbidden). It is narrow enough that it can be promoted to contracts later if a later session wants to.

### Filter shape — pure functions, one per axis
Each of the 7 filters is a standalone pure function of the same shape:

```ts
export interface FilterResult {
  readonly kept: readonly SyntheticBankRow[]
  readonly rejected: readonly ExclusionEntry[]  // {code, reason} from contracts.ts
  readonly stats: FilterStats
}
export interface FilterStats {
  readonly rowsIn: number
  readonly rowsKept: number
  readonly rowsRejected: number
}
export type FilterFn = (
  rows: readonly SyntheticBankRow[],
  plan: QueryPlan
) => FilterResult
```
Each filter: no I/O, no clock, deterministic, returns `{kept, rejected, stats}`. A failing IG-2 axis returns `CandidateGenerationResult` `ok:false` (Fatal) at the orchestrator level (see Pattern/LO below).

### Orchestrator — `runFilters`
Single public entry point applying filters in **`FILTER_EXECUTION_ORDER`** (imported unchanged from `contracts.ts`):

```ts
export interface FilterStageResult {
  readonly ok: true
  readonly rows: readonly SyntheticBankRow[]      // final filtered rows
  readonly rejectionLog: readonly ExclusionEntry[] // cumulative
  readonly perFilter: readonly PerFilterReport[]   // selectivity report (counts)
}
  | { readonly ok: false; readonly fatalDiagnostics: readonly FatalDiagnostic[] }

export interface PerFilterReport {
  readonly filterId: FilterId
  readonly stats: FilterStats
}

export function runFilters(
  adapter: BankReadAdapter,
  plan: QueryPlan,
  sink?: ObservabilitySink
): FilterStageResult
```
- Pulls `adapter.readMetadata()` once → feeds the 7 filters in order, threading each filter's `kept` into the next.
- Accumulates `rejected` into one cumulative `rejectionLog` (each entry tagged with its `CandidateRejectionReason` per the existing `contracts.ts` union).
- Emits a `CounterEvent('generator.filter.rows_reduced', { filter })` per filter to the optional sink (defaults to `noopSink`).
- Returns a deterministic `PerFilterReport[]` for selectivity instrumentation.

### The 7 filters — fixed order, exact behavior

| # | Filter | Admit rule | Reject reason (contracts.ts kind) |
|---|---|---|---|
| 1 | **exclusion** | `!plan.exclusions.includes(row.questionCode)` | `{kind:'excluded'; code}` |
| 2 | **status** | `row.status === 'Published'` | `{kind:'status'; code; status}` |
| 3 | **document** | `plan.permittedDocuments.includes(row.document)` | `{kind:'document'; code; document}` |
| 4 | **coverage** | see Coverage decision below | `{kind:'coverage'; code; detail}` |
| 5 | **difficulty** | `row.difficulty ∈ {Easy,Medium,Hard}` (the Query Plan enumerates all three per Set; this is a sanity/enum check, not a slot-count check) | `{kind:'difficulty'; code; difficulty}` |
| 6 | **pattern** | **IG-2 axis.** If the Bank column is entirely absent across all rows → `ok:false` Fatal (`missing_required_axis`, axis='question_pattern') per §4.2/§11.2. Per-row: a `null` pattern axis is **admitted** (incomplete → flagged later as reduced Confidence at Discovery, never silently dropped per §4.4). A non-null pattern outside the 6-value enum → rejected. | `{kind:'pattern'; code}` |
| 7 | **learning_objective** | **IG-2 axis.** Same fail-loud-on-missing-column rule as pattern. Per-row null admitted; out-of-enum rejected. | `{kind:'learning_objective'; code}` |

### Coverage Filter decision (your approval: Admit all / Maximum Recall)
The Coverage Filter is **per-Question** by nature, but two of the five rules are NOT per-Question predicates:
- **CR-3** — cross-Set cap → Solver concern (IG-5), not a per-row filter.
- **CR-5** — Section Sweep → requires IG-2 `section` axis (currently `null` since E-0 paused).
- **CR-2 / CR-4** — the spec/contract gives NO per-rule binding shape; the default fixture emits `binding: null` for all of CR-1..CR-5.

Per your decision: **a CoverageRequirement with a `null` (or otherwise per-Question-uninterpretable) binding admits the row** — the rule imposes no per-Question predicate at the filtering stage. Shortfall detection is deferred to Pool Validation (F-2.3, E-2D), never silently dropped at filtering. This honors §2.3 Invariant #2 (no info loss about eligibility) and §4.4 (filter doesn't weaken/drop).

When a **concrete CR-1 binding** IS present (`{ kind: 'document_topic_pairs', pairs: [{document, topic}, ...] }`), the filter narrows `binding: unknown` to that shape and admits a row iff it matches at least one `{document, topic}` pair. A binding of an **unrecognized shape** is treated as null → admit (Maximum Recall), not Fatal — the filter is not authorized to halt a run over a shape it hasn't been taught. The recognized CR-1 shape is the only one E-2C narrows; this is documented as additive (a future session can add CR-2/CR-4 narrowing).

### Document Filter — name, not id
`plan.permittedDocuments` carries document **names** (per `query-planner.ts:129-133`, it maps `documentRegistry.name`). The Document Filter matches `row.document` against names. The default fixture's `SyntheticBankRow.document = 'LAW-ACT-HED-2562'` is a document **id** — so tests that exercise the Document Filter happy-path will pass an explicit `document:` matching a registry entry's `name`. This is documented in JSDoc to prevent future confusion.

### Design note — why no wall-clock timing (F-2.2.2.1)
The backlog item says "per-filter row-count reduction **and timing**." But `lib/engine/README.md` §1 forbids `Date.now`/`process.hrtime` inside any pure module, and `shared/observability.ts` makes timing explicitly a **caller-measured** concern (`ModuleTimingEvent.durationMs` "is measured by the caller (Runtime API or the module wrapper), never by reading the clock inside the module"). E-2C therefore delivers **row-count reduction** (deterministic, assertable in tests) via `PerFilterReport.stats` + `CounterEvent` emission, and **defers timing** to the future Runtime API wrapper that owns the wall clock. This is the spec-consistent reading of F-2.2.2.1, not a scope cut.

## Test plan (`metadata-filters.test.ts`)
Runner style matches the existing generator tests (`node:assert/strict`, function-per-case, summary at end). Coverage:

**Per-filter correctness (one block per filter, ≥3 cases each):**
- exclusion: row in exclusions → rejected; not in → kept; empty exclusions → all kept.
- status: `'Published'` kept; `'Draft'`/`'Review'` rejected with reason carrying the status.
- document: matching name kept; non-matching rejected; empty registry → all rejected.
- coverage: null binding → admit all; concrete CR-1 binding → admit matching pairs, reject non-matching; unknown binding shape → admit all.
- difficulty: all three enum values kept; out-of-enum (e.g. `'Extra'` — via cast) rejected.
- pattern: column present → null admitted, valid values admitted, out-of-enum rejected; **column entirely absent across all rows → `ok:false` Fatal `missing_required_axis`**.
- learning_objective: mirror of pattern.

**Orchestrator / ordering:**
- `runFilters` applies filters in **exactly** `FILTER_EXECUTION_ORDER` (regression guard, F-2.2.2.2).
- Cumulative rejection log carries the correct per-filter reason kinds.
- Most-selective-first ordering is observable in `perFilter[].stats` (exclusion runs before document, etc.).

**Selectivity instrumentation (F-2.2.2.1, counts):**
- `PerFilterReport` rows-rejected counts add up to total rejected.
- A `CollectorSink` receives one `generator.filter.rows_reduced` counter per filter that rejected ≥1 row.
- `noopSink` default path doesn't throw.

**Architecture / purity:**
- `metadata-filters.ts` source has no `supabase`/`createClient`/`select(`/`Date.now`/`Math.random` references (string assertion on source).
- `runFilters` is deterministic: same adapter+plan → byte-identical `FilterStageResult` (via `stableStringify`).
- Immutability: rows fed in are never mutated (assert via stableStringify before/after).
- IG-2 fail-loud: when pattern column absent, `ok:false` with a `FatalDiagnostic` whose `category === 'missing_required_axis'` and `severity === 'Fatal'`.
